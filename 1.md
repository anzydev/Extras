## Missing Rate Limiting on Contact Form Submission

**Target:** `newtonschool.co`
**Affected endpoint:** `/api/v1/marketing/generic_form_response/h/{form_id}/update/`
**Vulnerability type:** Missing Rate Limiting / Unrestricted Form Submission

## Summary

The contact form submission endpoint does not appear to enforce effective rate limiting.

Multiple requests can be submitted repeatedly to the same endpoint without the server returning a rate-limit response such as `429 Too Many Requests`.

## Affected Functionality

The affected functionality is the public contact form available on the Newton School website.

The request is sent to:

```http
POST /api/v1/marketing/generic_form_response/h/{form_id}/update/
```

## Proof of Concept

A normal contact-form submission uses a request similar to:

```http
POST /api/v1/marketing/generic_form_response/h/{form_id}/update/
Content-Type: application/json
Authorization: Bearer <redacted>
```

Example request body:

```json
{
  "responseType": "PUBLIC_WEBSITE_CONTACT_FORM",
  "is_completed": true,
  "responseJson": {
    "full_name": "test",
    "email": "demo@example.com",
    "phone_number": "+910000000000",
    "what_do_you_need_help_with": "Admissions",
    "message": "test",
    "form_link": "https://university.newtonschool.co/v1/contact",
    "currentURL": "/v1/contact"
  }
}
```

When the request is submitted repeatedly, the endpoint continues accepting submissions instead of applying throttling.

## Expected Behavior

After a reasonable number of submissions within a short period, the server should temporarily reject further requests.

For example:

```http
HTTP/2 429 Too Many Requests
Retry-After: 60
```

## Observed Behavior

Repeated submissions are accepted by the endpoint without an effective rate limit being triggered.

## Impact

An attacker could potentially automate submissions to the contact form, resulting in:

* Contact-form spam
* Unwanted records being created
* Excessive backend/database requests
* Increased operational load
* Abuse of the form as a message-delivery mechanism

The practical impact depends on how the submitted data is processed downstream.

## Recommendation

Implement server-side rate limiting for the contact-form submission endpoint.

Possible controls include:

* IP-based rate limiting
* Per-account or token-based limits where applicable
* Per-form rate limits
* Request throttling with `429 Too Many Requests`
* Temporary blocking after repeated violations
* Duplicate-submission detection where appropriate

Rate limiting should be enforced **server-side** and should not rely solely on frontend restrictions.
